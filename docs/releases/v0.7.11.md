# Adaptive Agent Orchestrator v0.7.11

[简体中文](#简体中文) · [English](#english)

Release date: 2026-07-31

## 简体中文

### 解决的问题

长期审核会把问题分配给多个预声明阶段。上一阶段可以已经解决自己负责的
问题，同时保留应由后续阶段处理的 P0/P1。此前这里存在一个安全死锁：

- 只要仍有开放 P0/P1，上一阶段就不能生成最终主任务验收；
- 没有上一阶段的最终验收，下一条已声明里程碑又不能激活。

系统没有误放行，但合法的分阶段审核无法继续。开发者只能停下，不能靠改
plan、覆盖旧结果或假装所有问题已解决来绕过。

### 本版收益

- 新增一次性 scope-transition authorization，并要求它在下一阶段 activation
  之前写入。
- authorization 预先绑定 run、上一阶段、精确的下一阶段、selection 与
  checkpoint、控制材料、scope key、完整来源集合和问题计数。
- activation 必须消费同一份预授权。只在后续替换 scope key、控制材料、
  selection、run、milestone 或来源集合会 fail closed。
- 上一阶段的每条开放 P0/P1 都按来源/thread、finding ID、canonical ID、
  severity、exact text 与 text hash 守恒。
- 只有经同一来源复审的 occurrence 才能变为 resolved；其余问题必须原样
  carry forward，不能遗漏、降级、跨来源移动或只保留 canonical 汇总。
- scoped progression 只表示“本阶段边界已审、剩余问题已完整交给下一阶段”。
  它不是最终主任务验收，不能验证 main node、满足 completion 或跳过计划内
  阶段。

### 真实采用验证

修复后的安装版在 multi-divination 真实 37-event 长期审核 run 中完成：

- scope-transition 预授权成功；
- 计划内 Group2 activation 成功，并生成 schema 1.2 收据；
- journal 从 37 条追加到 39 条，没有改写旧历史；
- 11 条上一阶段 P1 中，4 条经同来源复审确认解决，7 条继续保留；
- completion 只报告 traditional 5 条、adversarial 2 条开放 P1，以及缺少
  最终 main-owner acceptance；
- 已解决的 P1-03 至 P1-06 没有回流。

该结果属于 `PASS_EXPECTED_BLOCKED`：阶段推进成功，而整个方法仍因真实未
解决问题安全阻断。multi-divination 产品文件没有被 Orchestrator 修改。

### 验证

- 48 个 PowerShell 脚本解析；
- 66 项恢复协议专项断言；
- 91 项 durable milestone/revision 专项断言；
- 799 项完整自测，59 个非法案例正确拒绝；
- 8 个 reference JSON 文件严格解析；
- Skill Creator 校验；
- 同一独立 Noether 角色对固定 commit/package 动态复攻 GREEN，
  P0/P1/P2 均为 0；
- 固定 ZIP 与安装副本 67/67 文件 SHA-256 一致；
- 真实控制面采用 PASS，且 completion 保持预期 BLOCKED。

### 边界

- 本版不修复平台 `systemError` 或 final 丢失本身。
- 本版不声明生产环境 Token 节省或业务准确率。
- 本版没有修改 multi-divination 产品文件；其中剩余 7 条 P1 是业务工作，
  不是 Orchestrator 缺陷。
- scoped progression 不能代替最终主任务验收，也不能让开放 P0/P1 消失。
- 本地追加式哈希链不能抵抗攻击者一致重写预授权事件及其后全部历史；该威胁
  需要外部不可变锚点。
- Windows 符号链接夹具因权限限制跳过；Linux/macOS 未动态验证。

编排 policy 仍为 `0.7.6`。v0.7.11 是该 policy 下的控制补丁，不要求改写
内部一致的现有 plan、run 或 journal。

## English

### The problem

Long-lived review assigns findings to multiple declared stages. One stage may
finish its own scope while intentionally retaining P0/P1 findings that belong
to later stages. That created a fail-closed deadlock:

- the current stage could not receive final main-owner acceptance while any
  P0/P1 remained open; and
- the next declared milestone could not activate without that final
  acceptance.

No stale evidence was accepted as success, but legitimate staged review could
not continue without rewriting the plan, replacing old results, or pretending
that every finding was resolved.

### Benefits

- A one-time scope-transition authorization is appended before the next
  milestone activation.
- Authorization pre-binds the run, previous milestone, exact next milestone,
  selection and checkpoint, controller material, scope key, complete source
  set, and finding counts.
- Activation must consume that exact earlier authorization. Replacing only the
  later scope key, controller material, selection, run, milestone, or source
  set fails closed.
- Every prior open P0/P1 occurrence is conserved by source/thread, finding ID,
  canonical ID, severity, exact text, and text hash.
- Only same-source reviewed occurrences may become resolved. Every other
  occurrence remains open; omission, downgrade, cross-source movement, or
  canonical-only aggregation is rejected.
- Scoped progression means only that the current stage boundary was reviewed
  and its remaining work was preserved for the next stage. It is not final
  main-owner acceptance and cannot validate the main node, satisfy completion,
  or skip a declared milestone.

### Real adoption

The installed fix ran against the real 37-event multi-divination durable-review
run:

- scope-transition authorization succeeded;
- the declared Group2 activation succeeded with a schema 1.2 receipt;
- the journal appended from 37 to 39 events without rewriting history;
- four of eleven prior P1 occurrences were resolved by same-source review and
  seven remained open;
- completion reported only five traditional and two adversarial P1
  occurrences, plus missing final main-owner acceptance; and
- resolved P1-03 through P1-06 did not reappear.

This was `PASS_EXPECTED_BLOCKED`: staged progression succeeded while the full
method remained safely blocked by real unfinished work. The Orchestrator did
not modify multi-divination product files.

### Validation

- 48 PowerShell scripts parsed;
- 66 focused recovery-protocol assertions;
- 91 durable-milestone/revision assertions;
- 799 full self-test assertions and 59 rejected invalid cases;
- 8 strict reference JSON parses;
- Skill Creator validation;
- the same independent Noether role dynamically re-attacked the fixed
  commit/package and returned GREEN with P0=0, P1=0, and P2=0;
- fixed ZIP and installed Skill copies matched 67/67 files by SHA-256; and
- the real control-plane adoption passed while completion remained correctly
  blocked.

### Boundaries

- This release does not repair platform `systemError` or missing-final
  behavior.
- It does not claim measured production Token savings or business accuracy.
- It did not modify multi-divination product files. Its seven remaining P1
  occurrences are product work, not Orchestrator defects.
- Scoped progression cannot replace final main-owner acceptance or make an
  open P0/P1 disappear.
- The local append-only hash chain does not resist coherent rewriting of the
  authorization event and all later retained history. That threat requires an
  external immutable anchor.
- The Windows symbolic-link fixture was skipped; Linux/macOS were not
  dynamically validated.

The orchestration policy remains `0.7.6`. v0.7.11 is a control patch under that
policy and does not require rewriting a consistent existing plan, run, or
journal.
