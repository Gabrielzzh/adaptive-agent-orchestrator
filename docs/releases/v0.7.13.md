# Adaptive Agent Orchestrator v0.7.13

[简体中文](#简体中文) · [English](#english)

Release date: 2026-07-31

## 简体中文

### 解决的问题

长期只读审核任务会跨多个里程碑和 checkpoint 持续复用。真实运行暴露了两处
安全阻塞：

1. 当前里程碑准备建立新恢复 cycle 时，生成器会枚举同一来源的旧 cycle，
   却用“当前里程碑”重新解释旧收据。旧收据本来合法，但因为属于更早里程碑，
   反而阻断当前 checkpoint 的 attempt-1。
2. 已固定的首里程碑版本复审在后续阶段继续工作后，会读取该来源“最近一次”
   completed/validated/adopted 事件，而不是当时已经写入选择收据的事件。
   后续合法事件因此会让旧选择被误判为证据变化。

两处都安全地 fail closed，没有放行错误结果，但会让长期审核无法继续回收正式
结论。

### 本版修复

- 每份历史恢复收据按它自己记录的里程碑与 activation epoch 验证，不再用
  当前 active milestone 重新解释。
- 当前 checkpoint 仍必须生成自己的确定性 cycle，绑定同一 run、source、
  role、thread、里程碑、checkpoint、input 与 attempt。
- recovery receipt 必须位于 run 的 canonical `receipts` 路径；复制到其他
  目录不能参与防重放或恢复。
- 旧版本复审选择按 `source_lifecycle_bindings` 中预先固定的 sequence/hash
  精确读取 completed、validated 与 adopted 事件，不再选择该来源后来发生的
  最新事件。
- 事件身份、顺序、状态、来源、thread、result/disposition 证据或排除清单有
  任一变化，仍在写 journal 前拒绝。

### 实际收益

长期领域专家或反方审核任务可以跨阶段继续工作：

- 合法的旧恢复 cycle 不再卡住新的 checkpoint；
- 后续阶段的合法生命周期不会使早先已固定的审核选择失效；
- 旧选择也不能借“读取最新事件”偷偷换成另一条同来源结果；
- 原任务恢复耗尽后，仍只允许一条经过授权、保持同角色连续性的 replacement
  路径，不会无限创建替代任务。

### 独立验收

原验收执行线程连续受到平台内容过滤而没有产生产品结论。主控随后明确授权了
且只授权了一个等价、只读、无下级 Agent 的 replacement reviewer，保留同一
验收责任和攻击集合。

该 reviewer 对固定 commit/package 完成：

- 2 条合法路径动态验证；
- 22 条相邻篡改与重放攻击，22/22 在 journal write 前拒绝；
- 旧版本复审选择在后续同来源事件存在时仍精确返回原 sequence 30/31/32；
- P0=0、P1=0、P2=0，最终结论 GREEN。

### 真实采用验证

安装后的候选在 multi-divination 的真实长期审核 run 中完成完整闭环：

- checkpoint13 的新恢复 cycle 与旧 Group1 cycle、当前 Group2 activation
  共存，生成器成功建立当前 attempt-1；
- 旧首里程碑选择按固定 sequence/hash 复验，`adopted -> result_pending`
  与后续恢复状态合法推进；
- 原 adversarial source 的当前 cycle 正式耗尽 3/3 后，只创建一个同角色、
  只读 replacement；
- replacement 使用自己的有界恢复 namespace，在 attempt-2 返回正式 final，
  没有创建 replacement-of-replacement；
- schema 1.3 replacement result 与 source-specific disposition 均生成，
  生命周期完整进入 completed、validated、adopted；
- 业务结论仍是 `FAIL/UNKNOWN`，九项 occurrence 全部保持 open；
- completion 继续因开放 P1、当前来源约束和缺少 main acceptance 安全
  `BLOCKED`。

这证明恢复与替代控制链可用，同时不会把“没有新增 finding”错误转换成业务
PASS。

- 69 项恢复协议专项断言；
- 106 项 durable milestone/revision 专项断言；
- 817 项完整自测，59 个非法案例正确拒绝；
- 8 个 reference JSON 文件严格解析；
- Skill Creator 校验；

### 边界

- 本版不修复平台 `systemError` 或 final 丢失本身。
- 本版不把证据未跑全的领域审查写成业务 PASS，也不判断 multi-divination
  的业务正确性。
- 本版不声明生产环境 Token 节省或业务准确率。
- 本版没有修改 multi-divination 产品文件。
- replacement 仍需明确授权、同来源/角色/thread/checkpoint/input 连续性，
  且不能再创建 replacement-of-replacement。
- 本地追加式哈希链不能抵抗攻击者一致重写早期授权与全部后续历史；该威胁
  需要外部不可变锚点。
- Windows 符号链接夹具因权限限制跳过；Linux/macOS 未动态验证。

编排 policy 仍为 `0.7.6`。v0.7.13 是该 policy 下的控制补丁，不要求改写
内部一致的现有 plan、run 或 journal。

## English

### The problem

Long-lived read-only review tasks continue across milestones and checkpoints.
Real adoption exposed two fail-closed blocks:

1. While creating a new recovery cycle under the current milestone, the
   generator enumerated an older same-source cycle but reinterpreted it against
   the current milestone. The older receipt was valid for its own milestone,
   yet it blocked the new checkpoint's attempt 1.
2. An immutable first-milestone revision selection later read the same source's
   most recent completed/validated/adopted events instead of the exact events
   already bound in the selection receipt. Valid later-stage work therefore
   made the older selection appear changed.

Both paths failed closed, but the durable review could not recover a formal
result.

### Fixes

- Validate every historical recovery receipt against its own recorded
  milestone and activation epoch, never the currently active milestone.
- Keep the current checkpoint's deterministic cycle bound to the same run,
  source, role, thread, milestone, checkpoint, input, and attempt.
- Require recovery receipts to remain under the run's canonical `receipts`
  directory. A copied receipt cannot participate in replay prevention or
  recovery.
- Read an immutable review revision's completed, validated, and adopted events
  by the exact sequence/hash pre-bound in `source_lifecycle_bindings`, not by
  whichever same-source events happened most recently.
- Continue rejecting any changed identity, ordering, state, source, thread,
  result/disposition evidence, or excluded-evidence manifest before journal
  write.

### Benefits

Long-lived domain and dissent reviewers can continue across stages:

- a valid older recovery cycle no longer blocks a new checkpoint;
- valid later-stage lifecycle events do not invalidate an earlier immutable
  selection;
- the earlier selection cannot silently substitute a newer same-source result;
  and
- after the original task exhausts recovery, only an authorized same-role
  replacement continuity path is allowed, preventing replacement proliferation.

### Independent acceptance

The original acceptance execution thread was repeatedly stopped by platform
content filtering and produced no product verdict. The controller then
explicitly authorized exactly one equivalent read-only replacement reviewer
with no worker delegation, preserving the same acceptance obligation and
minimum attack set.

That reviewer completed:

- 2 positive dynamic paths;
- 22 adjacent mutation and replay attacks, all rejected before journal write;
- exact recovery of the older selection's original sequences 30/31/32 despite
  later same-source lifecycle events; and
- GREEN with P0=0, P1=0, and P2=0.

### Real adoption

The installed candidate completed the full control path in the real
multi-divination durable-review run:

- checkpoint13 created a new recovery cycle alongside historical Group1 cycles
  and the current Group2 activation;
- the old first-milestone selection revalidated by exact sequence/hash, allowing
  legal `adopted -> result_pending` recovery progression;
- after the original adversarial source formally exhausted 3/3, exactly one
  same-role read-only replacement was created;
- the replacement used its own bounded recovery namespace and returned a formal
  final on attempt 2, without a replacement-of-replacement;
- schema 1.3 replacement result and source-specific disposition receipts were
  generated, followed by completed, validated, and adopted lifecycle events;
- the business outcome remained `FAIL/UNKNOWN`, with all nine occurrences open;
  and
- completion remained correctly `BLOCKED` by open P1, current-source
  constraints, and missing main acceptance.

The recovery and replacement controls therefore worked without turning “no new
finding” into a business PASS.

### Validation

- 48 PowerShell scripts parsed;
- 69 focused recovery-protocol assertions;
- 106 durable-milestone/revision assertions;
- 817 full self-test assertions and 59 rejected invalid cases;
- 8 strict reference JSON parses;
- Skill Creator validation;
- fixed ZIP, commit tree, and installed Skill matched 67/67 files;
- the equivalent independent replacement reviewer returned GREEN with
  P0=0/P1=0/P2=0; and
- real checkpoint13 original 3/3 → one replacement continuity → replacement
  recovery → formal result/disposition/lifecycle passed.

### Boundaries

- This release does not repair platform `systemError` or missing-final
  behavior.
- It does not turn incomplete domain evidence into a business PASS or judge
  multi-divination business correctness.
- It does not claim measured production Token savings or business accuracy.
- It did not modify multi-divination product files.
- A replacement still requires explicit authorization and matching
  source/role/thread/checkpoint/input continuity, and cannot create a
  replacement-of-replacement.
- The local append-only hash chain does not resist coherent rewriting of early
  authorization and all later history; that threat requires an external
  immutable anchor.
- The Windows symbolic-link fixture was skipped; Linux/macOS were not
  dynamically validated.

The orchestration policy remains `0.7.6`. v0.7.13 is a control patch under that
policy and does not require rewriting a consistent existing plan, run, or
journal.
