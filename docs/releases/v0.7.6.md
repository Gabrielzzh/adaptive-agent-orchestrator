# Adaptive Agent Orchestrator v0.7.6

[简体中文](#简体中文) · [English](#english)

Release date: 2026-07-30

## 简体中文

### 解决的问题

长期领域审核不会总在一个预先写好的里程碑列表内结束。真实采用中，一个
durable review run 已经用完最后一条声明里程碑，但仍有 17 条 P1 需要按
依赖分组修复，再交给原来的两个长期审核来源分别复审。

旧 run 的 plan、run metadata、genesis 和 journal 都必须保持不可变。直接
修改旧计划、复制整个目录或新建一个没有连续性证明的 run，都会丢失“这些
问题来自谁、由谁继续负责、哪些义务还没关闭”的审计链。

v0.7.6 增加正式的 durable-review successor-run 协议：旧 run 先导出一份
不可变的未完成义务快照，新 run 再通过绑定该快照的 adoption 收据创建。

### 本版收益

- predecessor export 精确绑定旧 plan、run、genesis、最终 journal head 与
  event count、effective policy、当前 milestone、checkpoint 和控制授权。
- 每个长期来源绑定自己的 role、thread、result/disposition 身份；一个来源
  不能替代另一个。
- 每条未解决 P1 绑定 source finding ID、canonical ID、原 severity、精确
  text hash 和 status。遗漏、改写或降级都会拒绝。
- successor 必须是全新的 v0.7.6 run，并声明自己的后续里程碑；不能复制旧
  目录、手改旧 journal、直接生成 genesis 或创建平行分叉。
- 继承的 P1 会成为新 run 的 baseline obligations。原来源没有逐项处置并
  完成同源复审前，completion 始终 `BLOCKED`。
- P0 不允许跨 run 携带；必须在旧 run 中解决，防止用“迁移”绕过最高风险门。
- one-main-writer、result-only、禁止 Worker 再派生 Worker、模型绑定、容量
  与现有 recovery/milestone 门保持不变。

### 正式操作顺序

1. 验证旧 run 与当前 policy activation、最终 journal head 和 active
   milestone 均一致。
2. 为 successor 编写新的不可变 plan，保留同两个 durable source 的 role
   与 thread 连续性，并声明新的 milestone 列表。
3. 用 `New-DurableReviewSuccessorExportReceipt.ps1` 在旧 run 生成一次性
   predecessor export。
4. 用 `New-OrchestrationSuccessorRun.ps1` 创建新 run 与 successor adoption
   收据；不要复制旧 run 目录。
5. 用 `Test-DurableReviewSuccessorAdoption.ps1` 验证 adoption，再运行
   `Test-OrchestrationCompletion.ps1`。在继承 P1 关闭前，预期结果是
   `BLOCKED`。

详细参数和拒绝边界见
`skills/adaptive-agent-orchestrator/references/workflow-contract.md`。

- 15 项 run-policy activation 专项断言；
- 45 项 recovery protocol 专项断言；
- 722 项完整自测断言；

### 边界

- 本 Skill 不修复平台 `systemError` 或 final 丢失。
- successor adoption 不迁移业务产物，也没有修改 multi-divination。
- 本版不声称已经证明生产环境 Token 节省。
- 本地哈希链仍需要外部保留的 head/hash 才能抵抗完整历史重写。
- Windows 符号链接夹具因权限限制跳过；Linux/macOS 未动态验证。

## English

### The problem

Durable domain and dissent review does not always finish inside one
predeclared milestone list. In the real adoption case, a durable review run had
used its last declared milestone while 17 P1 findings still needed grouped
repairs and separate re-review by the same two durable sources.

The predecessor plan, run metadata, genesis, and journal must remain immutable.
Editing the old plan, copying the directory, or starting an unbound run would
lose the audit trail for who raised each finding, who still owns its review, and
which obligations remain open.

v0.7.6 adds a formal durable-review successor-run protocol. The predecessor
exports one immutable snapshot of its unfinished obligations, and the new run
is created through an adoption receipt bound to that export.

### Benefits

- The predecessor export binds the old plan, run, genesis, final journal head
  and event count, effective policy, active milestone, checkpoint, and control
  authorization.
- Every durable source keeps its own role, thread, result, and disposition
  identity. Sources cannot substitute for one another.
- Every open P1 binds its source finding ID, canonical ID, original severity,
  exact text hash, and status. Omission, mutation, or downgrade fails closed.
- The successor is a new v0.7.6 run with its own declared milestones. Directory
  copying, old-journal edits, bare genesis, and parallel forks are rejected.
- Inherited P1 findings become baseline obligations. Completion remains
  `BLOCKED` until the original sources disposition and re-review them.
- P0 cannot be carried into a successor; it must be resolved in the predecessor.
- One main writer, result-only consumer output, no Worker nesting, model
  binding, capacity, recovery, and milestone gates remain intact.

### Formal operating sequence

1. Validate the predecessor, its active runtime policy, final journal boundary,
   and active milestone.
2. Create a new immutable successor plan with the same durable role/thread
   continuity and a new milestone list.
3. Run `New-DurableReviewSuccessorExportReceipt.ps1` once in the predecessor.
4. Run `New-OrchestrationSuccessorRun.ps1` to create the new run and adoption
   receipt. Do not copy the predecessor directory.
5. Validate with `Test-DurableReviewSuccessorAdoption.ps1`, then run
   `Test-OrchestrationCompletion.ps1`. `BLOCKED` is expected until inherited
   P1 findings are closed.

Exact parameters and negative boundaries are documented in
`skills/adaptive-agent-orchestrator/references/workflow-contract.md`.

### Validation

- all 41 PowerShell scripts parsed;
- 37 durable-milestone and successor-run assertions;
- 15 run-policy activation assertions;
- 45 recovery-protocol assertions;
- 722 full self-test assertions;
- 59 intentionally invalid cases rejected;
- all 8 reference JSON files strictly parsed;
- Skill Creator validation;
- dynamic re-attack by the same independent Noether reviewer ended with
  P0=0, P1=0, and P2=0; all 28/28 additional attacks passed;
- a temporary-copy adoption test of the real run inherited 17/17 P1 findings
  across two sources and correctly remained `BLOCKED`.

### Boundaries

- The Skill does not repair platform `systemError` or missing-final behavior.
- Successor adoption does not migrate business artifacts and did not modify
  multi-divination.
- This release does not claim measured production Token savings.
- Full-history rewrite resistance still needs an externally retained head/hash.
- The Windows symbolic-link fixture was skipped; Linux and macOS were not
  dynamically validated.
