# Adaptive Agent Orchestrator v0.7.10

[简体中文](#简体中文) · [English](#english)

Release date: 2026-07-30

## 简体中文

### 解决的问题

长期审核不是“一次审完就结束”。同一组领域专家与反方角色会在首个里程碑
内反复检查修改后的新版本。此前存在两个安全阻断：

1. 某个来源已经正式采纳上一版结论后，即使新 checkpoint 已建立合法的新
   恢复 cycle，状态机仍会拒绝它进入 `result_pending`。
2. 不可变 plan 只指向首个里程碑的初始审核结果。后续两组来源重新审查了
   最新 checkpoint，系统仍没有正式、不可歧义地选择这组新结论的路径。

系统均保持 fail closed，没有误放行；代价是合法复审无法继续，产品研发被
控制面阻断。

### 本版收益

- 已 adopted 的长期来源只有在存在一个未使用、合法的 schema 1.2
  attempt-1 cycle，且 checkpoint/input 确实不同的情况下，才能进入新一轮
  `result_pending`。
- 普通 `adopted` 仍是终态；缺 cycle、重放旧 cycle、同 checkpoint 重用、
  直接从 attempt 2/3 开始、跨 source/thread/milestone 均拒绝。
- 首个声明里程碑可在推进下一里程碑前创建一次追加式 revision
  authorization。
- authorization 在新结果产生前固定唯一 selection identity，并绑定 run、
  plan、当前日志边界、checkpoint/input、全部必需 source/role/thread、控制
  授权和锚点前的非完成证据。
- 每个必需的只读来源只能在该授权下重新启用一次，必须返回 fresh、
  cumulative 的 result/disposition；一方 PASS 不能替代另一方。
- selection 必须逐来源保存此前每个 finding occurrence 的 ID、原 severity、
  exact text/hash 与 canonical ID。新 checkpoint 不能让旧 P1 消失、降级或
  跨来源合并。
- completion 只读取唯一合法 selection，不按时间或文件名猜测“最新结果”；
  selection 不替代主 Agent 的独立验收，开放 P0/P1 继续阻断完成。

### 真实采用验证

multi-divination 的真实 27-event 长期审核 run 在 checkpoint10 完成了：

- revision authorization；
- traditional 与 adversarial 两个原只读来源的 fresh post-authorization
  复审；
- 两份 source-specific schema 1.3 result/disposition；
- 两条来源各自的 `completed → validated → adopted`；
- 唯一 revision selection。

两组 fresh final 均为 PASS，没有新增 P0/P1/P2。selection 精确选中
checkpoint10，保留 11 条后续 P1 source occurrences、0 条 P0；旧的已解决
问题没有回流，也没有被冒充为当前开放问题。随后占卜研发已进入下一组。

### 验证

- 47 个 PowerShell 脚本解析；
- 66 项恢复协议专项断言；
- 79 项 durable milestone/revision 专项断言；
- 787 项完整自测，59 个非法案例正确拒绝；
- 8 个 reference JSON 文件严格解析；
- Skill Creator 校验；
- 同一独立 Noether 角色对固定 commit/package 复攻 GREEN，无阻断发现；
- 固定 ZIP 与安装副本 66/66 文件原始 SHA-256 一致；Windows 工作树仅有
  CRLF/LF 差异，规范化后 66/66 一致；
- 真实控制面采用 PASS。

### 边界

- 本版不修复平台 `systemError` 或 final 丢失本身。
- 本版不声明生产环境 Token 节省或业务准确率。
- 本版没有修改 multi-divination 产品文件。
- revision 只适用于首个声明里程碑尚未推进下一里程碑的场景；不能覆盖
  plan、旧结果或历史事件，也不能把首里程碑结果冒充后续里程碑。
- 所有必需来源都必须重新审查；一份 PASS 不能替代另一来源。
- 本地哈希链不能抵抗攻击者一致重写全部保留历史；这需要外部不可变锚点。
- Windows 符号链接夹具因权限限制跳过；Linux/macOS 未动态验证。

编排 policy 仍为 `0.7.6`。v0.7.10 是该 policy 下的控制与兼容补丁，不要求
改写一致的现有 run。

## English

### The problem

Long-lived review is not a one-shot final check. The same domain and dissent
roles re-review repaired versions inside the first milestone. Two fail-closed
gaps blocked that legitimate workflow:

1. After a source had adopted an earlier result, the lifecycle rejected
   `result_pending` even when a valid recovery cycle existed for a new
   checkpoint.
2. The immutable plan selected only the first milestone's baseline results.
   There was no auditable, unambiguous way to select both sources' fresh results
   for a later checkpoint inside that same first milestone.

Neither gap accepted stale work as success, but both could stop product
development indefinitely.

### Benefits

- An adopted durable source may enter a new `result_pending` cycle only through
  an unused, valid schema 1.2 attempt-1 receipt for a different
  checkpoint/input.
- Ordinary `adopted` remains terminal. Missing or replayed cycles,
  same-checkpoint reuse, direct attempt 2/3 entry, and cross-source, thread, or
  milestone substitution fail closed.
- The first declared milestone may create one append-only revision
  authorization before advancing to a later milestone.
- Authorization fixes the only selection identity before fresh results exist
  and binds the run, plan, current journal boundary, checkpoint/input, complete
  source/role/thread set, controller authority, and pre-authorization
  non-completion evidence.
- Every required read-only source is re-armed once and must return fresh,
  cumulative source-specific results. One source's PASS cannot replace another.
- Selection conserves every earlier finding occurrence by source finding ID,
  original severity, exact text/hash, and canonical ID. A later checkpoint
  cannot silently drop, downgrade, merge, or move an obligation.
- Completion reads only the uniquely authorized selection, never the newest
  file or timestamp. Selection does not replace fresh main-owner acceptance,
  and open P0/P1 findings remain blockers.

### Real adoption

The real 27-event multi-divination durable-review run completed the checkpoint10
flow:

- revision authorization;
- fresh post-authorization reviews by the original traditional and adversarial
  read-only sources;
- two source-specific schema 1.3 result/disposition chains;
- separate `completed → validated → adopted` lifecycles; and
- one revision selection.

Both fresh finals passed with no new P0/P1/P2. The selection bound checkpoint10,
retained all 11 later P1 source occurrences and zero P0, and did not revive
resolved older findings as current work. Product development then advanced to
the next group.

### Validation

- 47 PowerShell scripts parsed;
- 66 focused recovery-protocol assertions;
- 79 durable-milestone/revision assertions;
- 787 full self-test assertions and 59 rejected invalid cases;
- 8 strict reference JSON parses;
- Skill Creator validation;
- the same independent Noether role returned GREEN for the fixed
  commit/package with no blocking finding;
- 66/66 fixed-ZIP and installed Skill files matched by raw SHA-256; the Windows
  working tree matched 66/66 after CRLF/LF normalization;
- the real control-plane adoption passed.

### Boundaries

- This release does not repair platform `systemError` or missing-final
  behavior.
- It does not claim measured production Token savings or business accuracy.
- It did not modify multi-divination product files.
- A revision applies only before the first declared milestone advances. It
  cannot overwrite the plan, old results, or historical events, or relabel
  first-milestone evidence as a later milestone.
- Every required source must re-review; one PASS cannot substitute for another.
- The local hash chain does not resist coherent rewriting of the complete
  retained history; that requires an external immutable anchor.
- The Windows symbolic-link fixture was skipped; Linux/macOS were not
  dynamically validated.

The orchestration policy remains `0.7.6`. v0.7.10 is a control and compatibility
patch under that policy and does not require rewriting a consistent existing
run.
